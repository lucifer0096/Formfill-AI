FormFill · rahul branch · accessibility log

What's accessible today, and what's still a gap

A working record of the four session pages, checked line by line against docs/ACCESSIBILITY.md — not a claim of full compliance.

01

Why this page exists

ACCESSIBILITY.md on main is explicit: for an app whose users are blind, an accessibility defect is a functional defect, not a polish item. This page is the honest answer to "does the code actually do what that spec says" for the four pages built on this branch — /review, /overview, /questions, /confirm.

How this was checked: by reading the spec section by section and testing each page's markup against it, not by assuming the existing patterns (inherited from Arya's upload page) already covered everything. Several real gaps were found and fixed this way — see §3.
02

Keyboard: what actually works right now

Everything is reachable by Tab on every page, per ACCESSIBILITY.md §3's "no exceptions" rule. /questions additionally supports the spec's single-key spoken-mode commands:

NNext question — same as pressing the Next/Finish button
PPrevious question
SpaceRepeat the current question (moves focus back to it)
HToggle the plain-language help text
SSkip — only fires when the field is optional
LRead the field's label verbatim, as printed on the source form
RSave the current answer set and jump straight to /confirm for review
Suspended while typing. §3 calls out "the app ate my typing" as the classic bug here — these single-key commands are disabled the moment focus is inside any <input> or <textarea>, checked directly against the event target rather than a global mode flag. This check is by tag name, not input type, so it also suspends single-key commands while focus is on a checkbox or radio button (e.g. answering a Yes/No question) — overly cautious there since no text is being typed, but consistent and never wrong in the direction that matters.

On this branch /questions and /confirm are separate routes rather than one page with an internal "reviewing" phase, so R is implemented as a real navigation (save answers, then router.push("/confirm")) rather than dispatching the engine's own REVIEW event — dispatching that event would just leave the user on /questions in an internal phase no UI on this branch renders. L dispatches the engine's existing VERBATIM event and shows the resulting announcement on screen (previously only spoken via the sr-only live region). The remaining pages (/review, /overview) still don't have these commands, since neither presents a single field to act on.

Implementation note for anyone extending these pages: focus handling now lives in one shared hook, src/lib/use-route-focus.ts — attach its ref to a page's <h1 tabIndex={-1}> rather than re-deriving this per page.

Clarifying the "heard N of M" row above: the visible on-screen counter itself is deliberately aria-hidden (it's a sighted convenience, not meant to interrupt with every single click) — the same information is announced through a separate, genuinely live Notice region lower on the page instead. Worth knowing if this ever gets refactored: the count you can see and the count that gets spoken are two different elements on purpose, not a duplicate.

The touch-target check covered every real interactive element: Button/LinkButton share a px-6 py-3 base that clears 44px well past the minimum; on /questions the radio/checkbox inputs for boolean and choice/multichoice fields are visually sr-only, but each is wrapped in a full-width <label> with its own px-4 py-3 padding, and that label — not the native control — is the actual click target. The only sub-44px element found was ProgressTrail's 24×24px step-number circles, which are aria-hidden and non-interactive (the step label text next to them isn't a link or button either), so they're decorative and out of scope for this check.

04

Known gaps — not yet built

Named explicitly so they don't get mistaken for "done" by omission.

No sr / spoken mode distinction.§1's two-audience problem — a screen-reader user needs the app acoustically silent, a non-screen-reader user needs it to speak aloud — isn't implemented at all on this branch. Everything here relies on the browser's own screen-reader support via correct markup; there's no speechSynthesis integration, no mode detection, and no Ctrl+Alt+S toggle. That's packages/speech's job on main, not yet wired into this branch.
No 400% zoom / reflow testing done.§4 and the definition-of-done checklist in §8 call for this on every PR. Not verified on this branch yet.
forced-colors / Windows High Contrast mode untested.Also part of §8's per-PR checklist; not verified here.
No screen-reader testing with a real AT.§8 requires NVDA or VoiceOver testing per PR. Everything on this page is markup-level correctness (roles, live regions, focus), not a substitute for that manual pass.
