What's accessible today, and what's still a gap

A working record of the four session pages, checked line by line against docs/ACCESSIBILITY.md. Not a claim of full compliance.

01

Why this page exists

ACCESSIBILITY.md is explicit: for an app whose users are blind, an accessibility defect is a functional defect, not a polish item. This page is the honest answer to "does the code actually do what that spec says" for the four core pages: /review, /overview, /questions, /confirm.

How this was checked: by reading the spec section by section and testing each page's markup against it, not by assuming the existing patterns (inherited from the upload page) already covered everything. Several real gaps were found and fixed this way, listed in the section below.
02

Keyboard: what actually works right now

Everything is reachable by Tab on every page, per the spec's "no exceptions" rule for keyboard access. /questions additionally supports the spec's single-key spoken-mode commands:

NNext question, same as pressing the Next/Finish button
PPrevious question
SpaceRepeat the current question (moves focus back to it)
HToggle the plain-language help text
SSkip, only fires when the field is optional
LRead the field's label verbatim, as printed on the source form
RSave the current answer set and jump straight to /confirm for review
Suspended while typing. The spec calls out "the app ate my typing" as the classic bug here. These single-key commands are disabled the moment focus is inside any <input> or <textarea>, checked directly against the event target rather than a global mode flag. This check is by tag name, not input type, so it also suspends single-key commands while focus is on a checkbox or radio button, for example when answering a Yes/No question. That is overly cautious there since no text is being typed, but consistent and never wrong in the direction that matters.

/questions and /confirm are separate routes rather than one page with an internal "reviewing" phase, so R is implemented as a real navigation (save answers, then router.push("/confirm")) rather than dispatching the engine's own REVIEW event, which would leave the user on /questions in an internal phase no current UI renders. L dispatches the engine's existing VERBATIM event and shows the resulting announcement on screen, previously only spoken via the sr-only live region. The remaining pages (/review, /overview) still don't have these commands, since neither presents a single field to act on.

Implementation note for anyone extending these pages: focus handling lives in one shared hook, src/lib/use-route-focus.ts. Attach its ref to a page's <h1 tabIndex={-1}> rather than re-deriving this per page.

Clarifying the "heard N of M" row above: the visible on-screen counter itself is deliberately aria-hidden, since it is a sighted convenience and not meant to interrupt with every single click. The same information is announced through a separate, genuinely live Notice region lower on the page instead. Worth knowing if this ever gets refactored: the count you can see and the count that gets spoken are two different elements on purpose, not a duplicate.

The touch-target check covered every real interactive element. Button/LinkButton share a px-6 py-3 base that clears 44px well past the minimum. On /questions the radio/checkbox inputs for boolean and choice/multichoice fields are visually sr-only, but each is wrapped in a full-width <label> with its own px-4 py-3 padding, and that label, not the native control, is the actual click target. The only sub-44px element found was ProgressTrail's 24×24px step-number circles, which are aria-hidden and non-interactive since the step label text next to them isn't a link or button either, so they are decorative and out of scope for this check.

04

Known gaps, not yet built

Named explicitly so they don't get mistaken for "done" by omission.

No automatic sr / spoken mode distinction.The spec's two-audience problem, where a screen-reader user needs the app acoustically silent while a non-screen-reader user needs it to speak aloud, isn't automatically resolved yet: there is no mode detection and no first-run prompt. A manual Read aloud control (button, or the global Ctrl+Alt+S shortcut) is built and live on /review, /overview, /questions, and /confirm, using the browser's own speechSynthesis through a single dedicated module (src/lib/speech) as the spec's own hard rule requires. It is deliberately manual only, never automatic, so it can never talk over a screen reader already running.
No 400% zoom / reflow testing done.The spec's definition-of-done checklist calls for this on every change. Not verified yet.
forced-colors / Windows High Contrast mode untested.Also part of the per-change checklist; not verified here.
No screen-reader testing with a real assistive technology.The spec requires NVDA or VoiceOver testing per change. Everything on this page is markup-level correctness (roles, live regions, focus), not a substitute for that manual pass.
