FormFill · rahul branch · scope for review

What's built, what's planned, and what the P0 demo should show

A single picture of scope, checked against main's own roadmap, not a guess at what "done" means.

01

How to read this

Three separate questions, often blurred together: what actually works today, what the project's own design docs call for eventually, and what's actually worth putting in front of someone at a demo. This page keeps those three apart on purpose.

Source of truth: main's docs/DESIGN.md §7 defines the roadmap as five phases, P0 through P4. This branch (rahul) was built independently and doesn't map onto those phases in strict order. It jumped straight to a working P1/P2 slice (real PDFs, both AcroForm and flat) without first building P0's standalone conversation engine on fixture forms, then back-filled P0's actual engine once the gap was noticed. That history is why the sections below are organised by capability, not by phase number.
02

What's genuinely working today

Verified by testing against real PDFs, not just by reading the code. Each of these has been exercised end to end at least once with real input.

AcroForm PDF reading Real fillable-field PDFs are read directly via pdf-lib. Every field kind (text, checkbox, radio, dropdown, multi-select, signature), instant, no model call.
AcroForm label detection When a field's own internal name is meaningless (common on auto-generated PDFs), the label physically printed next to it on the page is found instead, using the same text-layer extraction as the flat-PDF path. Local heuristic, no model.
Flat-PDF text extraction + classification PDFs with no real fields have their text and position extracted locally, then turned into plain-language questions by a model call, the one place in the app a network request happens.
PII redaction before every model call Names, emails, national ID numbers, addresses, and similar are stripped and replaced with placeholders before the classification request leaves the device, restored locally afterward. Fail-closed: if redaction itself fails, the call is aborted.
Conversation engine A pure state-machine reducer (ported from main's own packages/conversation) drives Answer and Confirm: real skip-logic, a two-step review gate, consistent spoken-style value formatting.
Document output Confirming produces a real download: a genuinely filled, flattened PDF for AcroForm uploads, or a question/answer summary PDF for classified ones.
Accessibility fundamentals Keyboard-only navigation, single-key commands in the Answer flow, focus management on every route/question change, aria-live regions, skip-to-content. Checked section by section against main's normative spec; see ACCESSIBILITY.html for the honest gap list.
Live deployment Deployed and redeployed after every change; testable by anyone at a public URL, not just locally.
03

Working, but with a known limitation

Large forms with repeated grids A per-row checklist (e.g. a property inspection table) has no "this is one row" concept yet, so every cell surfaces as its own question. Fine for most forms; a real problem on a few of the largest real-world ones tested.
Free-tier classification model Deliberately chosen for a $0 hackathon demo. Can be slow (up to 75s on a large form) or occasionally rate-limited. A one-line swap to a paid model removes this; see MODELS.html.
Emit for flat forms is a summary, not a marked-up copy No coordinate data exists yet to draw an answer back onto a flat PDF at its original position, so the download is a clean question/answer summary document instead. Honest, but not what DESIGN.md §4.5 ultimately describes for this case (a print-alignment overlay).

05

Recommendation: what the P0 demo should actually show

The goal of a demo is a clean story, not a feature count. Everything below is either strong enough to show as-is, or strong enough to show with a caveat said out loud; nothing here needs to be hidden or apologised for.

  1. Upload a real AcroForm PDF (a genuine fillable government form) The strongest path end to end: instant local reading, real labels found even when the PDF's own field names are meaningless, every field type rendered correctly, a genuinely filled PDF downloaded at the end. No caveats needed.
  2. Upload a flat/scanned-text PDF as a second example Shows the AI piece specifically: plain-language questions generated from officialese, PII redaction happening invisibly, low-confidence fields honestly flagged. Say the model is a free tier for cost reasons, note it can be slower.
  3. Walk the Answer flow with keyboard only N/P/Space/H/S single-key commands, focus always landing on the new question. This is the accessibility story, and it's real. Don't just describe it, drive it live.
  4. Trigger the review gate deliberately Try to confirm without reading every answer back first, show the exact "you haven't heard N of M" message, then confirm again to demonstrate the expert override. This single moment demonstrates the whole product thesis from DESIGN.md §3.5 ("nothing is submitted without read-back").

Worth mentioning, not worth demoing live

  • PII redaction is real and load-bearing, but invisible by design. Say it happens; don't try to visually prove it mid-demo (the earlier proof was inspecting server logs, not something to reproduce live).
  • The free-model latency risk: test the actual demo form against the live deployment beforehand. If it's borderline, either switch that one form for a smaller one, or be ready to narrate "usually a few seconds" while it loads.

Recommend leaving out entirely

  • A very large form with repeated grids (like the residential tenancy agreement used in testing): the "every cell is its own question" gap is real and would derail the demo's pacing. Save it for a "here's what we're tackling next" slide instead, framed as a known scope decision, not a bug.
  • An image or photo of a form is currently a dead end (correctly flagged, but a dead end). Don't open the door to "what about photos" unless asked.
