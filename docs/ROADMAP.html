FormFill · rahul branch · scope for review

What's built, what's planned, and what the P0 demo should show

A single picture of scope, checked against main's own roadmap, not a guess at what "done" means.

01

How to read this

Three separate questions, often blurred together: what actually works today, what the project's own design docs call for eventually, and what's actually worth putting in front of someone at a demo. This page keeps those three apart on purpose.

Source of truth: main's docs/DESIGN.md §7 defines the roadmap as five phases, P0 through P4. This branch (rahul) was built independently and doesn't map onto those phases in strict order. It jumped straight to a working P1/P2 slice (real PDFs, both AcroForm and flat) without first building P0's standalone conversation engine on fixture forms, then back-filled P0's actual engine once the gap was noticed. That history is why the sections below are organised by capability, not by phase number.
02

What's genuinely working today

Verified by testing against real PDFs, not just by reading the code. Each of these has been exercised end to end at least once with real input.

Pivot in progress, 2026-08-03. Per the 2026-08-02 meeting with Nigel, the ingest pipeline changed from local AcroForm/text-layer detection to a single multimodal model call for every PDF — see docs/INTEGRATION.html for the full reasoning and src/lib/ingest/_archive/README.md for what was archived. The cards below marked re-verify describe the previous pipeline's tested behaviour; they need re-testing against the new one before being called "working" again. UI ownership has also moved to the Arya branch — this branch's scope from here is the AI/ingest pipeline.
Multimodal PDF classification Every PDF — fillable or flat — is now sent whole to a multimodal model (Gemma 3 27B via OpenRouter, Nigel's recommendation) in one call, with real AcroForm field names given as context so the model can map its own detections back onto them for fill-back. Built; not yet tested against a real form for accuracy. needs testing
AcroForm field enumeration A small local pdf-lib pass lists real field names only — no position, no label guessing (that moved to the model). Replaces the old local detection/label-finding pipeline.
Conversation engine A pure state-machine reducer (ported from main's own packages/conversation) drives Answer and Confirm: real skip-logic, a two-step review gate, consistent spoken-style value formatting. Unaffected by the pivot.
Document output Confirming produces a real download: any field the model mapped to a real AcroForm name gets written into a filled, flattened PDF; everything else appears in a question/answer summary in the same document. fill-acroform.ts/summary-pdf.ts unchanged by the pivot — already worked per-field, not per-form.
Second-pass answer verification A different model reviews filled answers for genuine mistakes before submission (Nigel's reliability check). API route built and callable; not yet wired into a submit flow on either branch's UI. not wired in
Accessibility fundamentals Keyboard-only navigation, single-key commands in the Answer flow (including R jump-to-review and L verbatim-label readback), visible format hints shown before input, focus management on every route/question change, aria-live regions, skip-to-content, 44×44px touch targets verified on every interactive control. Built before the UI ownership moved to Arya; still true of this branch's own pages.
Live deployment Deployed and redeployed after every change; testable by anyone at a public URL, not just locally. Not redeployed since the pivot — held pending model choice, per plan.
03

Working, but with a known limitation

Model choice isn't final CLASSIFICATION_MODEL is still set to Gemma 3 27B in code, but testing has since moved past it: local Ollama testing (docs/MODELS.html §04/§04b) found gemma3:4b, qwen2.5vl:7b, and gemma4:26b all genuinely correct, and a follow-up 16-form cloud batch (§04c/§04d) found the free google/gemma-4-26b-a4b-it:free accurate whenever it succeeded (6/16 — the rest were free-tier congestion, not accuracy failures). No model has been swapped into CLASSIFICATION_MODEL yet pending a quieter real-world (non-batch) trial.
PII redaction doesn't cover this path Redaction only ever operated on extracted text; it can't inspect or redact PII rendered inside a PDF sent whole to the model. A real, disclosed tradeoff from the pivot — see docs/INTEGRATION.html §03.
Large forms with repeated grids A per-row checklist (e.g. a property inspection table) had no "this is one row" concept in the old pipeline, so every cell surfaced as its own question. Not yet re-tested against the new multimodal path — may or may not still be a problem.
Emit for flat forms is a summary, not a marked-up copy No coordinate data exists yet to draw an answer back onto a flat PDF at its original position, so the download is a clean question/answer summary document instead. Honest, but not what DESIGN.md §4.5 ultimately describes for this case (a print-alignment overlay).

On voice input specifically: DESIGN.md §6 already flags browser speech-to-text as a known-hard problem, because the built-in Web Speech API is cloud-backed (sends audio to Apple/Google) and inconsistent across browsers. The one option that could satisfy the "answers never leave the device" rule properly, rather than just disclosing around it, is an on-device model like Whisper running fully in the browser (via WASM/WebGPU, no server call). Real and buildable, but a substantial feature on its own: a multi-megabyte model download and cache on first use, real transcription latency on lower-end devices, and voice-activity detection to know when the user has stopped speaking, all before it even reaches the conversation engine. Scoped out for now rather than half-built.
05

Recommendation: what the P0 demo should actually show

The goal of a demo is a clean story, not a feature count. Everything below is either strong enough to show as-is, or strong enough to show with a caveat said out loud; nothing here needs to be hidden or apologised for.

This section predates the 2026-08-03 pivot and needs a fresh pass. The previous recommendation leaned on "instant local reading" and "PII redaction happening invisibly" as demo strengths — neither is accurate for the new multimodal pipeline (every PDF now makes a network call, and redaction doesn't cover this path at all). Rewrite this once local model testing has confirmed real-form accuracy; until then, treat the steps below as the shape of a demo, not a script to follow as written.
  1. Upload a real fillable PDF (a genuine government form) Needs re-verification: does the model still find every field correctly, and map enough of them back to real AcroForm names to produce a genuinely filled PDF at the end? Was "no caveats needed" under the old pipeline; status unknown under the new one until tested.
  2. Upload a flat/scanned-text PDF as a second example Shows the AI piece specifically: plain-language questions generated from officialese, low-confidence fields honestly flagged. The redaction claim needs to be dropped from this pitch — say plainly that this path sends the document itself to the model, not just extracted text.
  3. Walk the Answer flow with keyboard only N/P/Space/H/S/L/R single-key commands, visible format hints before typing, focus always landing on the new question. Unaffected by the pivot — still real, still worth driving live. (Now on the Arya branch's UI, not this branch's own pages, once that becomes the demo surface.)
  4. Trigger the review gate deliberately Try to confirm without reading every answer back first, show the exact "you haven't heard N of M" message, then confirm again to demonstrate the expert override. Unaffected by the pivot — this is conversation-engine behaviour, not ingest.

Worth mentioning, not worth demoing live

  • The pivot itself is a good story if asked "why not just use pdf-lib": explain briefly that local PDF-structure heuristics were tested against 10-15 real forms and were unreliable, not just occasionally wrong, and that a single model call replaced three separate paths.
  • Model latency: test the actual demo form against whichever model is chosen, live, beforehand. If it's borderline, either switch that one form for a smaller one, or be ready to narrate the wait.

Recommend leaving out entirely

  • A very large form with repeated grids (like the residential tenancy agreement used in earlier testing): the "every cell is its own question" gap was real under the old pipeline and hasn't been re-tested under the new one. Save it for a "here's what we're tackling next" slide if it's still a problem.
  • An image or photo of a non-PDF file is currently a dead end (correctly flagged, but a dead end). Scanned/image-only PDFs now go through the same multimodal path as any other PDF, so this caveat is narrower than it used to be — worth re-checking what it actually still covers.
