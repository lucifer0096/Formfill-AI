FormFill · project scope

What's built, what's planned, and what the P0 demo should show

A single picture of scope, checked against the project's own roadmap, not a guess at what "done" means.

01

How to read this

Three separate questions, often blurred together: what actually works today, what the project's own design documents call for eventually, and what is worth putting in front of someone at a demo. This page keeps those three apart intentionally.

Source of truth: the project's design document defines the roadmap as five phases, P0 through P4. Development did not map onto those phases in strict order; the team moved directly to a working P1/P2 slice (real PDFs, both AcroForm and flat) before building P0's standalone conversation engine on fixture forms, then filled in P0's engine once that gap was identified. That history is why the sections below are organised by capability, not by phase number.
02

What's genuinely working today

Verified by testing against real PDFs, not just by reading the code. Each of these has been exercised end to end at least once with real input.

Pipeline pivot. Following a meeting with the project mentor, the ingest pipeline changed from local AcroForm and text-layer detection to a single multimodal model call for every PDF; see the integration doc for the full reasoning and src/lib/ingest/_archive/README.md for what was archived.
Multimodal PDF classification Every PDF, fillable or flat, is sent whole to a multimodal model in one call, with real AcroForm field names given as context so the model can map its own detections back onto them for fill-back. Validated across local, free-tier, and paid model testing; see the model selection document for full results.
Image upload support A PNG or JPG photo or scan is sent to the same classification model, the same way a flat PDF already is. No AcroForm fields exist for a photo, so confirming always produces a question-and-answer summary document rather than a filled PDF, the same fallback a flat PDF with no fillable fields already uses.
AcroForm field enumeration A small local pdf-lib pass lists real field names only, with no position or label guessing, since that moved to the model. Replaces the earlier local detection and label-finding pipeline.
Conversation engine A pure state-machine reducer drives the Answer and Confirm flow: real skip-logic, a two-step review gate, and consistent spoken-style value formatting.
Document output Confirming produces a real download: any field the model mapped to a real AcroForm name is written into a filled, flattened PDF, and everything else appears in a question-and-answer summary in the same document.
Second-pass answer verification A different model reviews filled answers for genuine mistakes before submission and is called automatically on every download. If it flags a real issue, a non-blocking warning banner on the confirm page shows it in plain language; the download itself is never blocked by this check.
Accessibility fundamentals Keyboard-only navigation, single-key commands in the Answer flow (including jump-to-review and verbatim-label readback), visible format hints shown before input, focus management on every route and question change, live regions for screen readers, a skip-to-content link, and touch targets verified on every interactive control.
Manual read-aloud speech A Read aloud button on every core page, plus a global Ctrl+Alt+S shortcut, speaks that page's content using the browser's built-in speech synthesis. Deliberately manual only, since the app cannot yet detect whether a screen reader is already running; automatic mode switching remains a separate, not-started item below.
Live deployment Deployed and redeployed after each change, testable by anyone at a public URL rather than only locally.
03

Working, but with a known limitation

Model choice tested, but has a known gap The classification model is google/gemma-4-26b-a4b-it:free, validated across local testing and a 16-form OpenRouter batch; see the model selection document. Every success across every test was genuinely accurate. It has one real, repeatable gap: it consistently fails on official NZ government forms specifically, confirmed by retesting those forms individually to rule out batch congestion as the cause. The root cause remains unconfirmed; see the known risks document.
Personal information redaction doesn't cover this path Redaction only ever operated on extracted text and cannot inspect or redact personal information rendered inside a PDF sent whole to the model. A disclosed tradeoff from the pivot; see the integration document.
Large forms with repeated grids A per-row checklist, such as a property inspection table, has no concept of "this is one row" in the current pipeline, so every cell surfaces as its own question. Not yet re-tested against the current multimodal path.
Output for flat forms is a summary, not a marked-up copy No coordinate data exists yet to draw an answer back onto a flat PDF at its original position, so the download is a clean question-and-answer summary document instead. This is an honest limitation, not what the design document ultimately describes for this case, which is a print-alignment overlay.

On voice input specifically: the project's design document already flags browser speech-to-text as a difficult problem, since the built-in Web Speech API is cloud-backed, sending audio to a third-party provider, and inconsistent across browsers. The option that could satisfy the "answers never leave the device" principle properly, rather than disclosing around it, is an on-device model such as Whisper running entirely in the browser via WebAssembly or WebGPU, with no server call. This is real and buildable, but a substantial feature on its own: a multi-megabyte model download and cache on first use, real transcription latency on lower-end devices, and voice-activity detection to determine when the user has stopped speaking, all before reaching the conversation engine. Scoped out deliberately rather than half-built.
05

Recommendation: what the P0 demo should actually show

The goal of a demo is a clean story, not a feature count. Everything below is either strong enough to show as-is, or strong enough to show with a caveat stated explicitly; nothing here needs to be hidden or apologised for.

  1. Upload a real fillable PDF, a genuine government or business form The model finds fields correctly and maps enough of them back to real AcroForm names to produce a genuinely filled PDF at the end, confirmed across extensive testing. Avoid official New Zealand government forms specifically for a live demo, given the known limitation described above; a pre-recorded example is a safer choice if a government form needs to be shown.
  2. Upload a flat or scanned-text PDF as a second example Shows the AI capability directly: plain-language questions generated from formal language, with low-confidence fields honestly flagged. State plainly that this path sends the document itself to the model, not just extracted text, and that personal information redaction does not cover this path.
  3. Walk the Answer flow with keyboard only Single-key commands for next, previous, repeat, help, skip, verbatim label, and jump-to-review, visible format hints before typing, and focus always landing on the new question.
  4. Trigger the review gate deliberately Attempt to confirm without reading every answer back first, show the resulting warning message, then confirm again to demonstrate the expert override.

Worth mentioning, not worth demoing live

  • The pipeline pivot is a good answer if asked why the app doesn't simply parse the PDF locally: local PDF-structure heuristics were tested against 10 to 15 real forms and proved unreliable, not just occasionally wrong, and a single model call replaced three separate paths.
  • Model latency: test the actual demo form against whichever model is chosen, live, beforehand. If response time is borderline, either substitute a smaller form or be ready to narrate the wait.

Recommend leaving out entirely

  • A very large form with repeated grids, such as a residential tenancy agreement: the "every cell is its own question" limitation is real and has not yet been resolved. Reserve this for a "what we're tackling next" discussion if it comes up.
  • An image or photo of a non-PDF file is currently unsupported and correctly flagged as such. Scanned or image-only PDFs go through the same multimodal path as any other PDF, so this limitation applies narrowly, to non-PDF image files specifically.
