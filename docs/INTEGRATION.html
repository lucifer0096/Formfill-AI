FormFill · rahul branch · AI integration log

What's been built on the AI-integration side

A working record of the ingest, classification and UI-wiring work done on rahul, and what's still open.

01

Scope of this branch

Arya's Arya branch has the first page (upload) and the visual system. rahul branches off that and adds the four remaining session pages, plus a real pipeline behind them: a PDF goes in, and — for a growing set of cases — a set of classified questions comes out the other end.

Not merged into main or Arya. The team's existing packages/* on main (form-model, conversation engine, redact, validate) are the eventual source of truth for this logic, but reconciling this branch with them is deliberately deferred until the next sync with Nigel. Until then, the IR types here are hand-duplicated to match main's shape, not imported.
02

The pipeline, and how far it currently reaches

A file dropped on the upload page moves through three possible paths, in order, exactly as ARCHITECTURE.md §5.1 describes it. The first two are fully built; the third is a named, honest placeholder.

1 · AcroForm Real PDF form fields read directly with pdf-lib. No model call, no network. Exact fidelity.
2 · Text-layer + classify pdfjs-dist extracts text and position; OpenRouter turns it into labelled questions.
3 · Image / scan Flagged as needs-vision when there's no text layer at all. Not implemented.

Two real forms were used to test this — a NZ patient enrolment form and an IRD KiwiSaver deduction form. Both turned out to have no AcroForm fields, which is the common case for real-world forms, not an edge case. Both correctly fell through to path 2.

04

The shape the model has to produce

The classification prompt in classify.ts asks the model to return sections and fields matching this shape — the same Field contract the rest of the app (and eventually main's conversation engine) already expects.

// src/lib/openrouter/classify.ts → src/lib/form-model/types.ts
Field {
  label        // VERBATIM from the source text. Never paraphrased.
  spokenLabel  // plain-language rewrite, phrased as a question
  help         // optional — only if the label alone isn't self-explanatory
  type         // date | currency | choice | name | address | …
  required     // boolean, best guess from the source text
  constraints  // options[] for choice/multichoice fields
  confidence   // 0..1 — the model's own honesty check, never faked high
  anchor       // { region, page, rect } — flat-page anchor, no acroform to point to
}

Low-confidence fields aren't hidden — /review tags anything under 0.5 as "uncertain, please confirm this one," the same pattern main's packages/conversation already uses at the review gate.

05

One form, end to end, today

  1. UploadFile is picked or dropped. Nothing leaves the browser at this point.
  2. Extract, locallypdf-lib checks for AcroForm fields; if none, pdfjs-dist pulls text and position instead.
  3. Classify, if neededOnly the extracted text (never the PDF file) is sent to /api/understand, which calls OpenRouter and returns a classified Form.
  4. Review/review shows the detected questions with a confidence badge on each.
  5. Overview → Answer → ConfirmThe remaining three pages read the same stored Form and the user's actual answers — no more hardcoded sample data anywhere in the flow.
What's genuinely new here is that this is no longer four independent UI mockups. Upload a real form and the fields you see on every subsequent page are the ones actually read from that file.
06

Deliberate gaps — not bugs

No image/OCR path yet.A scanned photo or image-only PDF is flagged needs-vision and told plainly it isn't supported yet, rather than silently failing or guessing.
Not reconciled with main's packages/*.The IR types are duplicated by hand, not imported, so this branch can build and demo independently. Reconciling is a team decision, deferred to the Nigel sync.
Model choice is hardcoded.CLASSIFICATION_MODEL in client.ts is fixed to one model for now, to prove the pipeline works before deciding on static-vs-dynamic model selection.
"Confirm and finish" doesn't do anything yet.The review gate UI exists and correctly blocks on unheard answers, but there's no emit step (filled PDF, print overlay) behind it — that's downstream of this integration work.
