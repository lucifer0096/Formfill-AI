FormFill · rahul branch · AI integration log

What's been built on the AI-integration side

A working record of the ingest, classification and UI-wiring work done on rahul, and what's still open.

01

Scope of this branch

The UI work has moved to the Arya branch. rahul's focus from here is the AI/ingest pipeline: a PDF goes in, and a classified set of questions — mapped back onto any real fillable fields where possible — comes out the other end, ready for either branch's UI to consume.

Not merged into main or Arya. The team's existing packages/* on main are the eventual source of truth for this logic, but reconciling this branch with them (a real npm workspace import, not a copy) is deliberately deferred until the next sync with Nigel. Until then, form-model, conversation, validate, and redact are all hand-ported here, unmodified logic, matching main's shape rather than importing it.
02

The pipeline — rebuilt 2026-08-03 after the Nigel meeting

The three-path local-detection pipeline described in earlier versions of this page is gone. It's archived, not deleted, at src/lib/ingest/_archive/ — see that folder's README.md for the full reasoning. Every PDF now goes through one path: the whole document is sent to a multimodal model in a single call.

Why the pivot. Local AcroForm/text-layer detection was tested against 10-15 real forms and worked correctly on a minority of them — Nigel's framing was that this isn't an accuracy problem to keep patching, it's a reliability problem: "it's not that they're inaccurate, it's that they're unreliable... they'll work perfectly once out of every 10 times, then fine three out of ten, then completely break seven out of ten." PDF structure isn't standardised enough for a heuristic tuned against one PDF (Acrobat-generated, Word-exported, scanned) to generalise to the next one. The fix he recommended: stop trying to parse PDF structure locally, and let a multimodal model read the document the way a person would — visually.
1 · Field-name enumeration A small local pdf-lib pass lists real AcroForm field names only (no position, no label guessing) — src/lib/ingest/acroform-fields.ts. Empty list for flat/scanned forms.
2 · Classify The whole PDF, plus that field-name list as context, goes to OpenRouter in one call. The model returns structured questions and maps each one to a real field name where one applies.
3 · Emit Filled PDF for any field the model mapped to a real AcroForm name, summary PDF entries for the rest — a form can now be a genuine mix of both, not one or the other.
4 · Verify A second, different model checks the filled answers for real mistakes before submission (Nigel's reliability pass) — called from /confirm's handleFinish() on every download. Best-effort and not yet surfaced in the UI: a failure never blocks the download, and no warning is shown yet for issues it does find.

Model choice: real testing (local Ollama cycles and an OpenRouter cloud batch, both across several real forms) replaced Nigel's starting suggestion, Gemma 3 27B — CLASSIFICATION_MODEL is now google/gemma-4-26b-a4b-it:free, the only model that produced consistently correct results. It has a known gap on official NZ government forms specifically. See docs/MODELS.html for the full testing history and current pricing comparison.

03

What this costs on privacy — a disclosed tradeoff, not an oversight

Redaction no longer covers this path. src/lib/redact pattern-matches PII in extracted text — it has no way to inspect or redact information rendered inside a PDF's pages before those bytes are sent to the model. Nigel's framing on this tradeoff: most of these forms are public forms that are already in the cloud, and the whole premise of the pivot is that local extraction was too unreliable to keep building around. This is a real, disclosed change from the previous branch state (which redacted every outbound call, no exceptions) — worth saying out loud at a demo rather than leaving implicit.

05

The shape the model has to produce

The prompt in classify-pdf.ts asks the model to return sections and fields matching this shape — the same Field contract the rest of the app, including the conversation engine, already expects. New since the pivot: acroFieldName and page.

// src/lib/openrouter/classify-pdf.ts → src/lib/form-model/types.ts
Field {
  label          // VERBATIM as it appears on the form. Never paraphrased.
  spokenLabel    // plain-language rewrite, phrased as a question
  help           // optional — only if the label alone isn't self-explanatory
  type           // date | currency | choice | name | address | …
  required       // boolean, best guess from the form
  constraints    // options[] for choice/multichoice fields
  confidence     // 0..1 — the model's own honesty check, never faked high
  anchor         // { acroform, fieldName } if the model matched a real field,
                // otherwise { region, page, rect } — same Field, either anchor kind
}

Low-confidence fields aren't hidden — /review tags anything under 0.5 as "uncertain, please confirm this one," and the conversation engine surfaces the same signal again at the review gate on /confirm.

06

One form, end to end, today

  1. UploadFile is picked or dropped. Nothing leaves the browser until Continue is pressed.
  2. Enumerate real fields, locallyA quick pdf-lib pass lists any real AcroForm field names — no position, no label guessing, no model call for this step.
  3. ClassifyThe whole PDF, plus that field-name list, is sent to /api/understand in one multimodal call, which returns a classified Form.
  4. Review/review shows the detected questions with a confidence badge on each.
  5. Overview → Answer → ConfirmThe remaining three pages read the same stored Form and the user's actual answers.
  6. VerifyA different model checks the filled answers for real mistakes before submission — called automatically on every download, best-effort (never blocks it). The result isn't shown anywhere in the UI yet.
  7. DownloadConfirming produces a real file: any field the model mapped to a real AcroForm name gets written into a filled, flattened PDF; everything else appears in a question/answer summary PDF. A single form can produce both kinds of output in the same document now.
07

Deliberate gaps — not bugs

No image/OCR path for non-PDF files.A photo or non-PDF image is flagged needs-vision and told plainly it isn't supported yet, rather than silently failing or guessing. PDFs — including scanned/image-only ones — go through the multimodal path like any other PDF now.
PII redaction doesn't cover this path.See §02b above — a real, disclosed tradeoff, not an oversight.
Not reconciled with main's packages/*.The IR types are duplicated by hand, not imported, so this branch can build and demo independently. Reconciling is a team decision, deferred to the Nigel sync.
Model choice, tested but not fully bulletproof.CLASSIFICATION_MODEL is google/gemma-4-26b-a4b-it:free, validated across local and cloud test cycles — but it has a real, repeatable gap on official NZ government forms specifically, still unresolved. See docs/KNOWN-ISSUES.html.
Verification pass is wired in, but has no UI yet.The model call runs automatically on every download and its result is stored, but nothing in the UI surfaces it — a warning banner or an override gate is an open design decision for whoever picks up that UI work next.
Emit is real but simple.src/lib/emit/fill-acroform.ts writes answers into any real PDF fields the model mapped, and src/lib/emit/summary-pdf.ts covers everything else in the same download. Neither draws answers onto a flat PDF at their original visual position (a print overlay), so unmatched fields appear as a summary, not a marked-up copy.
