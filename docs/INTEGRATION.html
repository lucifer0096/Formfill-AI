FormFill · AI integration

What's been built on the AI-integration side

A working record of the ingest, classification, and UI-wiring work, and what remains open.

01

Scope of this document

This document covers the AI and ingest pipeline: a PDF is submitted, and a classified set of questions, mapped back onto any real fillable fields where possible, comes out the other end, ready for the UI to consume.

Not yet reconciled with the team's shared workspace packages. Those packages are the eventual source of truth for this logic, but reconciling this codebase with them (a real workspace import, not a copy) is deliberately deferred until the next team sync. Until then, form-model, conversation, validate, and redact are all hand-ported here with unmodified logic, matching the shared shape rather than importing it directly.
02

The pipeline

An earlier three-path local-detection pipeline is described in src/lib/ingest/_archive/README.md, archived rather than deleted, along with the full reasoning behind replacing it. Every PDF now goes through a single path: the whole document is sent to a multimodal model in one call.

Why this approach was chosen. Local AcroForm and text-layer detection was tested against 10 to 15 real forms and worked correctly on a minority of them. The project mentor's framing was that this is not an accuracy problem to keep patching but a reliability problem: results varied unpredictably between forms rather than failing consistently in a way that could be fixed. PDF structure is not standardised enough for a heuristic tuned against one PDF (Acrobat-generated, Word-exported, scanned) to generalise to the next. The recommended approach: stop parsing PDF structure locally, and let a multimodal model read the document the way a person would, visually.
1 · Field-name enumeration A small local pdf-lib pass lists real AcroForm field names only, with no position or label guessing (src/lib/ingest/acroform-fields.ts). Returns an empty list for flat or scanned forms.
2 · Classify The whole PDF, plus that field-name list as context, is sent to OpenRouter in one call. The model returns structured questions and maps each one to a real field name where applicable.
3 · Emit A filled PDF is produced for any field the model mapped to a real AcroForm name, with summary entries for the rest; a single form can now genuinely mix both output types.
4 · Verify A second, different model checks the filled answers for real mistakes before submission, called automatically on every download. This is best-effort and not yet surfaced in the UI: a failure never blocks the download, and no warning is currently shown for issues it finds.

Model choice: real testing, including local model cycles and an OpenRouter cloud batch across several real forms, replaced the mentor's starting suggestion, Gemma 3 27B. The classification model is now google/gemma-4-26b-a4b-it:free, the only model that produced consistently correct results. It has a known gap on official NZ government forms specifically. See the model selection document for the full testing history and current pricing comparison.

03

The privacy cost: a disclosed tradeoff, not an oversight

Redaction no longer covers this path. src/lib/redact pattern-matches personal information in extracted text; it has no way to inspect or redact information rendered inside a PDF's pages before those bytes are sent to the model. The mentor's framing on this tradeoff: most of these forms are public forms already handled in the cloud, and the premise of this approach is that local extraction proved too unreliable to justify building around it. This is a real, disclosed change from the earlier state, in which every outbound call was redacted with no exceptions, and should be stated explicitly at a demo rather than left implicit.

05

The shape the model has to produce

The prompt in classify-pdf.ts asks the model to return sections and fields matching this shape, the same Field contract the rest of the app, including the conversation engine, already expects. acroFieldName and page are specific to this pipeline.

// src/lib/openrouter/classify-pdf.ts, src/lib/form-model/types.ts
Field {
  label          // verbatim as it appears on the form, never paraphrased
  spokenLabel    // plain-language rewrite, phrased as a question
  help           // optional, only if the label alone isn't self-explanatory
  type           // date | currency | choice | name | address | …
  required       // boolean, best guess from the form
  constraints    // options[] for choice/multichoice fields
  confidence     // 0 to 1, the model's own honesty check, never faked high
  anchor         // { acroform, fieldName } if the model matched a real field,
                // otherwise { region, page, rect }; same Field, either anchor kind
}

Low-confidence fields are not hidden: the review page tags anything under 0.5 as "uncertain, please confirm this one," and the conversation engine surfaces the same signal again at the review gate on the confirm page.

06

One form, end to end, today

  1. UploadThe file is selected or dropped. Nothing leaves the browser until Continue is pressed.
  2. Enumerate real fields, locallyA quick pdf-lib pass lists any real AcroForm field names, with no position, label guessing, or model call at this step.
  3. ClassifyThe whole PDF, plus that field-name list, is sent to /api/understand in one multimodal call, which returns a classified Form.
  4. ReviewThe review page shows the detected questions with a confidence badge on each.
  5. Overview, Answer, ConfirmThe remaining three pages read the same stored Form and the user's actual answers.
  6. VerifyA different model checks the filled answers for real mistakes before submission, called automatically on every download, best-effort, and never blocking. If it flags a real issue, a warning banner on the confirm page shows it in plain language.
  7. DownloadConfirming produces a real file: any field the model mapped to a real AcroForm name is written into a filled, flattened PDF, and everything else appears in a question-and-answer summary PDF. A single form can produce both kinds of output in the same document.
07

Deliberate gaps, not bugs

Personal information redaction doesn't cover this path.See the privacy section above; a real, disclosed tradeoff, not an oversight.
Not reconciled with the shared workspace packages.The intermediate representation types are duplicated by hand rather than imported, so this codebase can build and demo independently. Reconciling is a team decision, deferred to the next sync.
Model choice, tested but not fully bulletproof.The classification model is validated across local and cloud test cycles, but has a real, repeatable gap on official NZ government forms specifically, still unresolved. See the known risks document.
Output is real but simple.src/lib/emit/fill-acroform.ts writes answers into any real PDF fields the model mapped, and src/lib/emit/summary-pdf.ts covers everything else in the same download. Neither draws answers onto a flat PDF at their original visual position, so unmatched fields appear as a summary rather than a marked-up copy.
