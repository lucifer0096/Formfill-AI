FormFill · rahul branch · known risks

Things that can break, and what to do about them

A plain list of real risks found while building and testing. These are things that actually happened, not hypotheticals.

01

How to read this page

Each item below is rated by how likely it is to actually cause a problem during a demo or real use, not by how bad it would theoretically be. Most were found by testing with real forms, not guessed at.

02

Risks likely to matter for a live demo

Personal information in a PDF is no longer redacted before the AI call High

Since the 2026-08-03 pivot to a single multimodal classification call (see INTEGRATION.html), the whole PDF is sent to the model, not just extracted text. Redaction (src/lib/redact) only ever pattern-matched PII in text — it has no way to inspect or redact information rendered inside a PDF's pages before those bytes leave the device. This is a real, deliberate tradeoff agreed with Nigel (most of these forms are public forms already in the cloud, and local extraction was too unreliable to keep building the previous redaction step around), not an oversight — but it should be said out loud at a demo, not left implicit.

Status: disclosed tradeoff, not currently mitigated. If this needs to change later, redaction would have to move to either a pre-send image-level pass or be dropped in favour of per-model provider privacy terms.
Best-known model still isn't fully reliable under sustained load Medium

Local testing (see MODELS.html §04/§04b) found three working local models across two forms: gemma3:4b, qwen2.5vl:7b, and gemma4:26b (the mentor-recommended model) — all produced genuinely correct results. A follow-up cloud round tested free OpenRouter models across 16 real forms (MODELS.html §04c/§04d): google/gemma-4-26b-a4b-it:free succeeded on 6/16 with every success genuinely accurate, but slowed down and started timing out partway through a large back-to-back batch before recovering — most likely free-tier congestion under sustained load, not a flaw in the model itself. Two other free candidates (gemma-4-31b-it:free, Nvidia's Nemotron) never completed a single run in that batch due to rate-limiting and timeouts, so neither is ruled out on accuracy, only on availability so far.

Status: a demo-viable model exists (gemma-4-26b-a4b-it:free, or the local gemma3:4b/gemma4:26b), but hasn't been proven reliable under heavy concurrent load. A single-form real-world trial, not a back-to-back batch, is the fairer next test before committing to a production model.
The AI model can be slow on large, dense forms Medium

In the 16-form cloud batch, the two longest/densest forms (a 26-page citizenship application, a 13-page sponsorship form) were among several that timed out at the 2-minute test limit — though a 3-page form also timed out during the same batch, so form length alone doesn't fully explain it (see the load-related entry above).

Mitigation in place: the server is configured to wait up to 60 seconds, the maximum allowed on the current hosting plan, instead of giving up early. Before any live demo, test the actual form you plan to use against the live site once. If it's slow, have a smaller backup form ready, or switch to a paid model (see the model & pricing doc) for guaranteed speed.
OpenRouter's own PDF-reading step can go down independently of any model Medium

During the 16-form cloud batch (MODELS.html §04d), one form failed identically and instantly on all three models tested with "Failed to parse." The error detail showed OpenRouter uses a separate, shared document-reading service (from Mistral) to turn a PDF into readable text before any model sees it — and that service was briefly unavailable, unrelated to model choice.

Status: disclosed, not yet mitigated — no retry-on-parse-failure logic exists in classify-pdf.ts today. A simple one-retry-after-delay would likely cover transient outages like this one.
Scanned photos and image-only forms aren't supported Medium

Only PDFs work today, either with real fillable fields, or flat PDFs with readable text. A photo of a paper form, or a scanned image with no text layer, is detected and clearly flagged as unsupported rather than failing silently.

Recommendation: for any demo, use a real PDF (either kind above), not a photo.
03

Risks that were found and already fixed

Listed for transparency. These happened during development and are resolved, not currently live issues.

A page could freeze/crash on certain forms Fixed

Uploading a real large form once caused the review page to crash with a "maximum update depth exceeded" error, a technical bug where the page kept re-checking the same data in a loop. Found through real testing, root-caused, and fixed the same day, then verified with a full re-test.

Setting the AI service key on the live site broke every request Fixed

A hidden character got included by accident when saving the AI service's access key to the hosting platform, which caused every request to fail with a confusing error. Traced to the exact cause and fixed by re-saving the key a different way.

Personal information wasn't being stripped before the AI call Fixed, then superseded — see §02

Text extracted from flat forms was sent to the classification model as-is, with no check for names, emails, national ID numbers, or similar personal details it might contain. Fixed by porting the same detection logic the team's shared codebase already uses, and confirmed by inspecting the exact text sent to the model during testing: real names and email addresses were replaced with placeholders before leaving the server. This fix no longer applies — the 2026-08-03 pivot sends the whole PDF to the model instead of extracted text, which the redaction step can't inspect. See the new high-severity entry above.

Checkboxes on real PDFs showed as a text box, and field labels were meaningless Fixed

Testing against a real government form with real fillable fields surfaced two separate bugs: checkboxes and multiple-choice fields rendered as a free-text box instead of something you tick, and on a form whose fields were auto-named by whatever tool built it (things like "001", "002"), those meaningless internal names were shown as the question itself. Fixed by rendering the right control per field type, and by finding the actual label text printed next to each field on the page (no AI model involved — a local, position-based lookup) instead of relying on the field's internal name.

04

Things to keep in mind, lower urgency

Filled-document output only covers two cases Known gap

"Confirm and finish" now produces a real download: a genuinely filled PDF for forms with real fillable fields, or a plain question/answer summary for forms that were read as flat text. There's no in-between yet, for example drawing answers onto a flat PDF at their original position, so a flat form's output is a summary document rather than a marked-up copy of the original.

Not yet reconciled with the team's shared code (main branch) Known gap

This branch was built independently to move quickly for the hackathon. Four of main's engine packages (form-model, conversation, validate, redact) have since been ported over with their logic unmodified, so the two branches now behave the same way in those areas — but this is still a hand-copy, not a real npm workspace import, so a genuine merge is intentionally scheduled for after the next team sync, not something skipped by accident.

Large forms with repeated grids surface every cell as its own question Known gap

A form built as a table (e.g. a per-room property condition checklist, or a per-person schedule) has no concept of "this is one row" in the current field model — every individual box shows up as a separate question in the flow. Real for genuinely large government/legal forms; no grouping heuristic has been built for it yet.

No accounts, no saved history between sessions By design, for now

Closing the browser tab clears everything. This matches the project's privacy-first goal (nothing is stored on a server) but means there's no way to resume a form later. Worth flagging as a product decision to revisit, not a bug.
