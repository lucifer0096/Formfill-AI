FormFill · orientation for the build

What we are building, and how the pieces fit

A plain-language map of the four design docs — enough to hold the whole system in your head while we write code.

01

The product in one breath

A blind person opens a form — a PDF, a scan, a photo of paper, or a web page — and FormFill talks them through it one question at a time, checks their answers, reads everything back, and hands them a correctly filled document. Alone. Without showing their income or their diagnoses to anyone.

The docs are emphatic that the goal is not "read the form aloud". Screen readers already do that badly. The goal is a finished artefact — a filled PDF in the downloads folder — produced independently and correctly.

Why this matters for coding decisions: when a trade-off comes up, the tie-breaker is almost always "which option gets a correct, finished form with less help from a sighted person". That's why, for example, autofill offers a value instead of silently filling it — a stale address the user can't see is a real harm on a benefits claim.
02

The one idea that makes the codebase small

Three ways a form gets in (PDF, photo, web page) times three ways it gets out (filled PDF, print overlay, live web page) would normally mean nine separate code paths, each with its own bugs.

Instead, every input is converted immediately into one shared data structure — the Form IR ("intermediate representation"). Everything in the middle of the app only ever sees that structure. It has no idea whether the form came from a scanner or a website.

Ingest PDF parsing, OCR, reading a web page. Knows about file formats.
Core · the Form IR Conversation, validation, speech, profile. Knows nothing about files.
Emit Write the PDF, draw the overlay, fill the web page. Knows about file formats again.

The trick that lets the core stay ignorant: each field carries an anchor — a small tag saying where this field came from and therefore how to write a value back. That is the only source-specific thing that survives into the core.

// The shape everything else depends on (packages/form-model)
Field {
  label        // VERBATIM from the form. Never paraphrased.
  spokenLabel  // plain-language rewrite — what gets read aloud
  help         // what the question is actually asking
  type         // date | currency | choice | signature | …
  required     // boolean
  constraints  // maxLength, pattern, min, max, options
  sensitivity  // none | pii | sensitive  ← gates what may leave the device
  confidence   // 0..1 — how sure we are we read it right
  anchor       // ← the only source-specific part:
               //   { acroform, fieldName }  a real PDF form field
               //   { region, page, rect }   a box on a flat scan
               //   { dom, selector }        an input on a live page
  dependsOn    // skip-logic: only ask this if…
}

Answers are stored separately from the form. That isn't a style choice — it's what makes "structure may go to the cloud, answers never do" enforceable in code rather than merely promised, because the two are never in the same object.

03

The three rules that constrain everything

Most design decisions in this project fall out of three commitments. If a piece of code breaks one of these, it's a bug even if it works.

1 · Answers never leave the device. Form structure (labels, boxes, layout) may be sent to Claude to be understood — after personal data is stripped out and replaced with placeholders like ⟨PERSON_1⟩. Answers are handled entirely by local code. There is no server database and no accounts at all, so there is nothing to breach.
2 · Never the only voice in the room. If the user has a screen reader, our app must be acoustically silent and speak only through ARIA live regions. If they don't, our app must speak. Getting this wrong gives you either two voices talking over each other or a mute app — both completely unusable. Enforced mechanically: exactly one file in the whole codebase may call speechSynthesis.speak(), and a lint rule blocks the rest.
3 · Nothing is submitted without read-back. Every answer is read back, in order, before anything is written or submitted. This gate cannot be skipped. On a benefits or immigration form, a mis-parsed question has real consequences.

Plus one structural rule you'll hit while coding

The conversation package may not import any ingest or emit package, and may not touch the DOM. It is a pure function: (Form, Answers, Event) → (Answers, Announcements). That's what lets the most important logic in the product be tested exhaustively without a browser — and it's why the announcement transcripts are snapshot-tested. A change in what the user hears shows up as a reviewable diff.

04

One form, end to end

What actually happens when someone opens a PDF:

  1. CaptureThe file lands in the browser. Nothing is uploaded — the PDF bytes never leave the machine.
  2. Look for real form fieldsMany government PDFs have proper embedded fields (an "AcroForm"). If so, we build the Form IR straight from them and make no network call at all. This is the entire first shipping phase.
  3. Otherwise: extract, redact, understandPull out text and box positions on-device, strip anything personal into typed placeholders, send only that redacted structure to /api/understand, get back sections, field types and plain-language rewrites, then restore the placeholders locally.
  4. ConverseThe state machine walks the fields one at a time. Each one is announced, answered by typing or dictation or an autofill offer, and validated locally and immediately. Skip-logic means irrelevant branches are never read aloud — saving someone forty questions they don't need is worth more than any other optimisation here.
  5. ReviewLinear read-back of every field and answer, with a count of anything skipped or uncertain. Mandatory.
  6. EmitReal form fields get values written exactly. Flat scans get text drawn at the detected coordinates. Paper additionally gets a print-alignment overlay. Web forms get filled — but the user presses submit, not us.
Why a Web Worker keeps coming up: OCR takes seconds. On the main thread that freezes the UI and stalls the speech queue — the voice cuts out mid-sentence. So everything CPU-heavy runs in a worker, and the app can keep saying "I'm reading page two of four…".

The order of work, and why

  • P0 — Skeleton. Form IR, conversation engine, review gate, accessible shell, fixture forms. Built before any file parsing, because the conversation is the product.
  • P1 — PDFs with real form fields. Highest fidelity, zero OCR risk, no network call. The first genuinely useful thing.
  • P2 — Flat PDFs and scans. On-device OCR and model-based classification. Unlocks most real-world forms.
  • P3 — Camera capture. Guiding someone who can't see the lens to frame a page by audio alone. The hardest problem in the product; deliberately deferred.
  • P4 — Browser extension. Live web forms, reusing everything above.
06

Vocabulary

Terms that will come up constantly between us. Knowing these makes the rest of the conversation fast.

Form IR
The single normalised description of a form that the whole core operates on. "IR" = intermediate representation.
anchor
The tag on each field saying how to write a value back to its origin — a PDF field name, a rectangle on a page, or a CSS selector.
AcroForm
A PDF with genuine, machine-readable form fields, as opposed to a flat picture of a form. The easy, high-fidelity path.
flat PDF
A PDF that's really just an image. No fields, often no usable text. Needs OCR and geometry.
spokenLabel
The plain-language rewrite of an officialese question. The verbatim original is always one keystroke away and never discarded.
announcement
Something the app needs the user to know, emitted by the engine as data — text plus a priority. The UI decides whether that becomes speech or an ARIA live region.
sr mode / spoken mode
The two mutually exclusive modes. In sr mode the app is silent; in spoken mode it talks. When unsure, default to silent — silence is recoverable, double-speech drives users away.
redaction recall
The share of real personal data our detectors catch. CI gates on recall, not accuracy: a false positive costs a slightly worse result, a miss is a leak.
fail closed
If redaction can't complete, we do not send the request. Degrade to local heuristics and say so.
sensitivity
Per-field: none, pii, or sensitive. Sensitive fields are hard-blocked from cloud speech recognition, from logs, and from crash reports.
announcement transcript
A snapshot test of everything the user would hear for a given form. Reviewing it means reading it as if listening.
07

Decisions waiting on you

These are open in the docs, and a few of them change what we'd write in the very next session. Flagging them so they don't get decided by accident.

UK first or US first?This is the one with real code consequences right now. It determines the PII detectors (NI number vs SSN), the validators (postcode vs ZIP), and which fixture forms we build against. Everything in redact and validate branches off it.
Does the app shell come next, or more engine?Right now there is logic but nothing to open in a browser. We could scaffold apps/web so you can hear the conversation working, or keep hardening the engine against fixtures first.
Is full offline mode a v1 requirement?The PDF-with-real-fields path already needs no network. A full offline mode (installable app, local models) is a bigger commitment.
Support-worker mode?One of the four personas is a support worker helping twenty clients a week. A supervised mode is genuinely useful — and sits awkwardly against "answers never leave the device".
Compliance floor.WCAG 2.2 AA is assumed throughout. Whether EN 301 549 or Section 508 conformance is a formal target depends on whether public-sector procurement is in view.
