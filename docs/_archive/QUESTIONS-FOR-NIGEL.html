Questions, grounded in what's actually built

Not hypotheticals — every question below points at a real, specific decision or tradeoff already made on this branch.

01

Architecture & reconciliation

Four of your packages (form-model, conversation, validate, redact) are now hand-copied into this branch with unmodified logic. Is that copy accurate enough to reconcile as a straight import, or has anything on main moved on since?

Why this matters: the copies were made from a specific point-in-time read of main's packages. If those have changed since, the merge isn't a simple "delete the copy, add the workspace dependency" swap.

This branch never imported packages/* as a real npm workspace dependency, by design, so it could build and demo independently of the monorepo. Is that still the right call, or should the next piece of work be wiring the workspace up properly instead of building more features on the hand-copy?

Why this matters: every feature built from here forward either widens the gap to reconcile later, or gets built on top of code that's about to be replaced. Worth deciding which, deliberately.

02

Model & cost

Your architecture doc specifies calling Claude directly. This branch goes through OpenRouter instead, currently on a free-tier model, chosen specifically because cost isn't a concern for a hackathon demo. Is OpenRouter an acceptable long-term choice, or was Claude-direct a firmer requirement than "what we happened to use for the prototype"?

Why this matters: switching back to Claude direct is a small code change but a real one, and it changes the pricing/latency tradeoffs documented in MODELS.html.

The free model has taken up to 75 seconds on a large real form during testing. Is that an acceptable ceiling for a real (non-demo) user, or does moving to a paid model need to happen before this goes anywhere beyond a hackathon context?

Why this matters: this is a one-line swap technically, but a real budget decision, not something to default into silently.

03

Privacy & security

PII redaction (stripping names, emails, national ID numbers, etc. before any model call) has now been ported and verified working. Does the detector list need expanding for the jurisdictions you actually care about, beyond what's currently covered (UK/US patterns)?

Why this matters: DESIGN.md's open questions section explicitly flags UK-vs-US jurisdiction as an undecided call that changes the PII detector, the validators, and the fixture set. This branch inherited whatever main already had, not a jurisdiction decision of its own.

A real OpenRouter API key was shared directly in a chat session during development and has been in active use since. Does it need rotating before this branch is treated as anything other than a private demo?

Why this matters: low urgency for a hackathon, genuinely relevant the moment this becomes anything more permanent or gets a wider audience.

04

Scope & sequencing

This branch built P1 and P2 of your roadmap (AcroForm PDFs, then flat PDFs/scans) before P0's conversation engine actually existed as its own thing, which has since been back-filled. Given that history, what should the next phase actually be: P2's remaining piece (image/OCR support), or should the priority be closing gaps against the P0/P1 definition of done first (autofill profile, screen-reader testing)?

Why this matters: both are legitimate next steps and both are real work. Worth a team call on sequencing rather than continuing to build in whatever order testing happens to surface next.

Large real-world forms with repeated grids (a per-row property checklist, a per-person schedule) currently surface every individual cell as its own question, no grouping. Is this worth solving as its own piece of work, or is it acceptable to treat as a known edge case for now?

Why this matters: it's not on your original roadmap at all, found only through testing against real government/legal PDFs. Worth deciding whether it's in scope before more effort goes toward it.
