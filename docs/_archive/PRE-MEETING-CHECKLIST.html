FormFill · rahul branch · pre-meeting checklist

Before the next Nigel meeting

Three kinds of items: things worth building, things worth verifying, and things that need a decision from the wider team.

01

How to use this

Not everything here is equally urgent. Read the tag on each item: verify items are fast (minutes, no code) and should happen regardless of time; build items are real work and worth triaging against how much time is actually left; decide items aren't yours to resolve alone; bring them to the meeting itself rather than trying to close them beforehand.

02

Verify — fast, no code, do these regardless of time left

Test the actual demo form against the live deploymentverify

Not localhost. The free classification model has taken up to 75 seconds on a large real form in testing; if the form you plan to demo is borderline, you want to know that before the meeting, not during it. See KNOWN-ISSUES.html for the specifics.

Confirm the AcroForm PDF you plan to demo actually has real fillable fieldsverify

Open it in a PDF viewer first and check you can click into boxes and type. A flat/scanned PDF that only looks fillable will silently fall through to the classification path instead, which is a different (and less impressive) demo moment than intended.

Re-check all 7 routes are still live after the last deployverify

curl or open each of /, /review, /overview, /questions, /confirm, /help, /accessibility on the production URL. Thirty seconds, catches a bad deploy before Nigel does.

Walk through the review-gate override live, once, beforehandverify

Confirm without reading every answer, see the exact warning text, confirm again to override. This is the single strongest accessibility-story moment in the product (see ROADMAP.html §5); worth rehearsing the exact keystrokes once so it's smooth live.

03

Build — real work, worth doing if time allows

Field grouping for repeated gridsbuild

The known gap found while testing against a real residential tenancy PDF: a per-row checklist surfaces every cell as its own question instead of one grouped question. Not required for a clean demo (avoid that form specifically, per ROADMAP.html §5), but worth having an answer ready if Nigel asks how large real-world forms are handled.

A screen-reader pass with a real AT (NVDA or VoiceOver)build

Everything shipped so far is markup-level correctness (roles, live regions, focus management), never verified against an actual screen reader. main's own definition-of-done checklist requires this per PR. The single highest-value gap to close given the product's actual thesis.

400% zoom / reflow and forced-colors testingbuild

Also required by main's per-PR checklist, also not done yet on this branch. Faster to close than the screen-reader pass: mostly a manual browser-settings check, not new code.

Local autofill profilebuild

DESIGN.md's own definition of "done" for v1 explicitly includes "with their address and DOB autofilled." Currently nothing is remembered between forms. A real, if partial, gap against the project's own v1 bar, not just a nice-to-have.

04

Decide — bring these to Nigel, don't try to resolve alone

When and how to reconcile with main's packages/*decide

Four of main's packages (form-model, conversation, validate, redact) have already been hand-ported into this branch with unmodified logic, so behavior matches, but it's a copy, not an npm workspace import. The actual merge has been deliberately deferred pending this meeting. Worth deciding a concrete next step, not just "later."

Whether to rotate the OpenRouter API keydecide

A real key was pasted directly into a chat session and has been in active use since. Fine for a hackathon demo; worth a second opinion on whether it needs rotating before anything more permanent happens with this branch.

Free vs. paid model for anything beyond the demodecide

The free-tier model has genuine reliability tradeoffs (latency, occasional rate limits) documented in KNOWN-ISSUES.html. Fine as a deliberate hackathon-cost decision; not a decision that should silently carry forward past the demo without someone signing off on it.

Which roadmap phase to tackle nextdecide

ROADMAP.html lists everything not yet started, mapped to main's own P0-P4 phases (image/OCR support, camera capture, browser extension, spoken/speech-synthesis mode). Worth a team decision on sequencing rather than continuing to build in the order that happened to come up during testing.
