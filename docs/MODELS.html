Which AI model reads your forms, and what it costs

A plain-language explanation of the model choice behind form classification, and what the alternatives would cost.

01

Where AI actually gets used

Every uploaded PDF is read by a multimodal AI model, which turns it into a list of plain questions and, where the form has real fillable fields, maps its own detections back onto them. Most of the rest of the app — moving between questions, saving your answers, producing the final document — needs no AI at all.

Pivot, 2026-08-03: this used to be two paths — real PDF fields were read locally with no AI involved, and only "flat" forms without fields went to a model. Local field-detection turned out to be unreliable across real-world PDFs (tested against 10-15 real forms), so every PDF now goes through the same model call. See the integration doc for the full reasoning. This means AI usage is no longer occasional — it happens on every upload, not just flat ones.
02

How the model is accessed: OpenRouter

Rather than signing up with one AI company directly, FormFill goes through OpenRouter, a single service that gives access to models from many different providers (OpenAI, Google, Anthropic, Meta, and others) through one connection and one bill.

  • Flexibility: switching models is a one-line change in the code, not a new integration.
  • Price comparison in one place: every model's cost is visible side by side, so the cheapest option that still does the job well can be picked deliberately.
  • Free options exist: several capable models are available at no cost. This project currently uses one of them, described below.
03

What FormFill targets today

src/lib/openrouter/client.ts currently targets google/gemma-3-27b-it (Gemma 3 27B) via OpenRouter — cheap and multimodal, recommended in a 2026-08-02 review as a starting point.

Not finalised. Two real test cycles ran 2026-08-04 on two different forms (see §04 and §04b below), both against a shrunk 4-model set. gemma4:e4b failed correctness on both forms and is being dropped from rotation. gemma3:4b, qwen2.5vl:7b, and gemma4:26b all succeeded on both — the remaining decision is speed vs. marginal accuracy between those three, plus a third form still to come.
Local test set, chosen to cover different sizes and architecture families: gemma3:4b, gemma4:e4b, gemma4:26b, qwen2.5vl:3b, qwen2.5vl:7b, llama3.2-vision:11b, and minicpm-v (a document-OCR specialist, worth including since reading a form is closer to OCR than general image captioning). deepseek-r1 is kept separately as a candidate for the second-pass answer-verification step (§05), which is text-only and doesn't need vision.
04

First real test cycle — 2026-08-04

Ran the full 7-model local set (npm run test:ui) against one real form, FHP-Statutory-Declaration-Form.pdf (a multi-page statutory declaration with mixed field types: text, choice, boolean, file-attachment references, a signature line). Hardware: Intel i7-10610U, 4C/8T mobile CPU, 32GB RAM, no usable GPU (Intel UHD, ~1GB VRAM) — every model ran on CPU alone. Timeout was 20 minutes for this cycle (raised to 60 minutes afterward — see the note below).

Model Result Time Notes
gemma3:4b success 628s Only clean result. Correct title, 6 sensible sections, 13 fields with correct types (name, text, address, choice, date, signature). One cosmetic issue: stray ”,, characters appended to several labels — the model echoing its own JSON-formatting punctuation into the label text.
qwen2.5vl:3b timed out 1200s (cap) Never finished — ollama ps confirmed it stayed loaded and active the whole time, not stuck. No verdict either way at this timeout length.
gemma4:e4b failed 307s Finished fast but returned a confidently wrong response claiming no PDF/image was received at all (confidence: 1 on a fabricated "please provide the source document" field) — a real correctness failure, not a speed one.
qwen2.5vl:7b timed out 1200s (cap) Same as the 3b version — no verdict yet at 20 minutes.
minicpm-v failed 870s Finished, but broke the response schema: invented a "file" field type outside the allowed list, three bare string entries ("officialStampSection") inside what should be an array of field objects, and confidence: 1 on literally every field regardless of ambiguity — the prompt explicitly calls for honest low-confidence flags, so this isn't calibrating at all.
llama3.2-vision:11b failed 1.7s Hard failure, not a hardware/timeout issue: error loading model: unknown model architecture: 'mllama' — this Ollama build doesn't support this model's architecture at all. Retesting won't help without an Ollama update.
gemma4:26b timed out 1200s (cap) Nigel's actual recommendation — never got a real verdict at 20 minutes. Worth one retest at the new 60-minute timeout before ruling out.
Timeout raised from 20 to 60 minutes after this cycle (scripts/model-test-lib.ts). Three of the seven models hit the 20-minute cap without a real result either way — confirmed still genuinely working via ollama ps, not stuck. A separate root-cause fix landed the same day: Node's global fetch is built on undici, whose default 300-second headersTimeout was silently failing every model taking longer than 5 minutes with a bare "fetch failed", before this file's own timeout logic ever got a chance to apply. Fixed by using undici's fetch directly with a custom Agent.

Read after this cycle: narrow the next test round to gemma3:4b (confirmed baseline), qwen2.5vl:7b, and gemma4:26b (both unresolved, worth one retest at 60 minutes — the latter is Nigel's own pick). qwen2.5vl:3b, gemma4:e4b, minicpm-v, and llama3.2-vision:11b are deprioritised: the first three failed on correctness rather than just running out of time, and the last has a hard compatibility wall unrelated to timeout or prompting.

04b

Second test cycle — 2026-08-04, ACC claim form

Ran the shrunk 4-model set (gemma3:4b, gemma4:e4b, qwen2.5vl:7b, gemma4:26b) against a different real form, acc-form.pdf (a 3-page NZ ACC injury claim: mixed text/date/choice fields, a conditional "previous claim" section, an authorisation/declaration block, and a signature line). Same hardware as §04. Timeout: 60 minutes (raised after the first cycle). All four models finished — no timeouts this time.

Model Result Time Notes
gemma3:4b success 313s Best result of the cycle. Correctly grouped all sections including the declaration, sensible spokenLabel/help text on every field, high confidence throughout, no fabrication.
gemma4:e4b failed 310s Fabricated the entire form. Returned a fully-formed but completely unrelated "Membership Enrollment Form" (emergency contact, signature, payment frequency fields) with high confidence scores — not a timeout or a refusal, a confident hallucination. This is the model's second correctness failure in a row on two different forms (see §04's "no PDF received" failure). Recommend dropping it from the rotation.
qwen2.5vl:7b success 878s Correct and thorough across all 3 pages, but ~3x slower than gemma3:4b and missing help text on most fields. One field typed "unknown" at confidence 0.5 rather than guessing — arguably better calibration, not a flaw.
gemma4:26b success 1183s (~20 min) Nigel's pick. Correct and slightly more thorough section grouping (correctly isolated the conditional "if you already filed a claim" fields), very high confidence (0.95–0.98 across the board). By far the slowest of the four — on CPU-only hardware, ~4x gemma3:4b's time for a modest accuracy edge.
Read after this cycle: gemma4:e4b is out — two forms, two confident fabrications, worse than a slow-but-correct model or an honest failure. The real decision is now gemma3:4b (fastest, accurate) vs. gemma4:26b (Nigel's pick, marginally higher confidence, ~4x slower) vs. qwen2.5vl:7b (correct but slow, thinner on help text). A third form is planned before committing to a final pick.
04c

Third test round — trying the same models in the cloud

Everything above was run on Rahul's own laptop, which has no dedicated graphics card — that's why some of those runs took 15–20 minutes. This round asks a different question: if the same kind of model runs on OpenRouter's servers instead (rented, professional-grade hardware), how much faster does it get, and does it still read forms correctly?

In plain terms: a "model" here is the AI that looks at an uploaded form and works out what questions it's asking, so the app can read them aloud and let someone answer by voice or text. Two things matter for picking one: does it get the form right (no invented questions, no missed ones), and how fast/cheap is it to run for every person who uses the app. This section tracks both, in something closer to plain English than the technical tables above.

Test set so far: google/gemma-4-26b-a4b-it, using its free tier (a version of Google's Gemma 4 model that OpenRouter hosts at no cost) — the closest cloud match to Nigel's own recommendation, which was tested locally in §04b. More models and forms are being added to this table as tests continue.

Form tested Got it right? How long it took What it cost In plain terms
ACC injury claim form yes 32 seconds $0 (free tier) Correctly found every section of the form (claim details, previous-claim details, the signed declaration) and phrased each one as a clear spoken question. Compare to the same model family locally, which took 20 minutes on Rahul's laptop for a similar form — the cloud version is roughly 35–40x faster.
First Home Partner statutory declaration yes 93 seconds $0 (free tier) This is a genuinely hard form — dense legal paragraphs with multiple conditions bundled into single sentences (e.g. residency status, relationship status, and property ownership all phrased as long legal declarations). The model correctly broke each paragraph down into a clear yes/no question a person could actually answer out loud, without inventing anything or missing a condition. This is the strongest result of any test so far, local or cloud.
About the "$0" cost: OpenRouter's free tier genuinely does not charge — no money has been loaded into the account and nothing has been billed. (The raw API response briefly showed a small non-zero "cost" figure for free-tier calls; this turned out to be a reference number some providers report even on free routes, not a real charge, and the table/tool have since been corrected to only show real costs for paid models.)

Early read: the free cloud version of Nigel's recommended model is matching or beating every local result so far, at zero cost and a fraction of the time. If this holds up across more forms, it's a strong candidate to replace the current production model (google/gemma-3-27b-it, §03) — same family, free instead of paid, dramatically faster since it isn't limited by anyone's laptop hardware.

Pulled live from OpenRouter's models API on 2026-08-04, per 1 million tokens (roughly 750,000 words), for reading the input (a whole PDF now, not just extracted text — bigger payload than before the pivot) and for the response. A single form classification uses a small fraction of a million tokens either way, so treat this as a rate rather than a per-form cost. Every model below must support image/document input — a text-only model can't do this job at all now.

06

The second model: answer verification

Since the pivot, a second, independent model call can review a filled-out form for genuine mistakes before submission — deliberately a different model from classification, so the same blind spot can't pass its own check (src/lib/openrouter/verify-answers.ts, /api/verify). This step is text-only (it reads field labels and typed answers, not the PDF itself), so it doesn't need vision, and can be a much cheaper model than classification.

Current target: anthropic/claude-haiku-4.5, set in VERIFICATION_MODEL. deepseek-r1 is downloaded locally as a candidate to test against it — both are plausible, neither is finalised. The route exists and works standalone; it isn't yet called from a submit flow on either branch's UI.
07

If a different classification model turns out to work better

The change is a one-line edit in src/lib/openrouter/client.ts (CLASSIFICATION_MODEL). No redesign needed — classify-pdf.ts and the prompt itself don't assume anything model-specific beyond "accepts a PDF file and returns JSON."
